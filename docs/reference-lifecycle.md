# 对象引用怎样保持可用

`ObjectRef` 是当前游戏进程内的观察句柄，携带 `sessionId`、`worldEpoch`、`id` 和类型。人物／物品等长期目标应保存游戏 `ThingID`，需要操作时重新定位；不要把 `obj:*` 当作跨读档的存档 ID。

引用表现在有最多100,000个索引，正反向索引不强持有被观察对象。游戏仍持有且尚未被淘汰的同一个对象，反复读取、解析都会沿用同一ID并更新最近使用顺序。每次登记最多检查8个旧条目，逐步扫除GC已经回收的目标；达到容量时淘汰最久未使用的句柄，继续接受新引用。

| 情况 | 返回行为 | 调用方处理 |
| --- | --- | --- |
| 进程重启、读档或新建世界 | `STALE_REFERENCE`，会话／世界不匹配 | 从新会话、根对象或ThingID重新查询 |
| 已登记的对象被GC回收，或句柄因容量被淘汰 | `STALE_REFERENCE`，`details.reason=reference-expired` | 从原持有者、查询路径或ThingID取得新引用 |
| 句柄仍在表中，但游戏Thing已销毁 | `TARGET_GONE` | 重新观察目标结果，不重发原动作 |
| ID从未登记或格式无效 | `TARGET_GONE` | 修正定位，不把它当作有效目标 |

没有按秒计的统一失效时间。临时任务、临时集合和其他已经不被游戏持有的对象可以随GC失效；需要长久保存的数据应在一次观察内用 `fields` 读成值，在进程外计算和保存。引用失效只影响句柄，不会删除、修改或销毁游戏对象。

`session.status.referenceCache` 提供 `capacity`、`indexed`、`issued`、`collected`、`evicted`。`indexed` 包括尚未被增量扫描清理的弱条目，并不等于仍存活的游戏对象数。更换世界会清空索引和本世界清理计数，ID序号继续单调增加，旧ID永不分配给新对象。

针对这张实际引用表的独立C#回归位于 `tests/dotnet`，直接编译桥接使用的源文件；不依赖复用底座的202项测试来代表新增逻辑覆盖。长期实机表现仍与一次回归／容量压力测试分开记录。
